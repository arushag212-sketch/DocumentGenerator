# PROJECT: Smart Document Generator for ACM SVNIT Surat

You are building a reusable, template-driven document automation system for a student club (ACM SVNIT). Read this whole file, then start at Phase 0. Do not skip the phase gates.

## 1. Goal
Convert event/activity requirements (a form or a natural-language sentence) into standardized, editable club documents (DOCX and PDF) using real DOCX templates, with consistent branding. The LLM is only ONE step (extraction and narrative drafting). Documents come from DOCX templates filled by code.

Example input the system must handle:
"We are conducting a two-day Web Development Workshop on 14–15 October in Seminar Hall for around 120 students."
Expected: extract event name, type=workshop, dates, venue, participant count; recommend Permission Letter + Event Approval Note; list what is missing (see section 8); never invent it.

## 3. Non-negotiable rules
1. NEVER fabricate official details: reference/approval numbers, amounts, bill/invoice numbers, GST numbers, bank/PAN details, supplier names, sanction numbers, names of judges/signatories, roll numbers, mobile numbers. If missing, ask the user. Anything an LLM guessed is flagged "unconfirmed" and blocks finalization until the user confirms it.
2. All arithmetic (line totals, totals, GST, grand totals, amount in words in Indian numbering) is done in code with Decimal. Never by the LLM.
3. One canonical Event Record is the single source of truth. Every document reads from it, so event name, dates, venue and amounts are identical everywhere. Changing a field and re-rendering updates all documents.
4. Templates are real DOCX files plus a schema, in folders. Adding or editing a template must need NO code change (except registering a brand-new computed function, see 6.3).
5. Do not hardcode documents, events or event/document combinations. Hardcode nothing club-specific in Python; it lives in `club_config.yaml` and template folders.
6. Preserve source wording faithfully, including known typos in official forms ("NATIOINAL", "Moblie"). List them in `docs/TEMPLATE_NOTES.md` for the club to decide. Do not silently "fix" official form text.
7. Output must be consistent: fonts, spacing, headers/footers and branding come from the DOCX templates, never from ad-hoc code formatting.
8. Personal data (bank accounts, PAN, mobiles) is sensitive: store minimally, mask in UI and logs (show last 4 digits), keep real config files out of git (`.gitignore`), commit only `*.example.yaml` with placeholders.
9. The workflow must be automated end to end. The user must never copy AI output into Word manually.

## 4. Architecture
```
Input (form | natural language | pasted notes)
  -> Extractor: rules + dateparser + regex first; LLM (strict JSON schema) as fallback
  -> Canonical Event Record (validated, each field tagged with its source)
  -> Doc-type recommender (event type + lifecycle stage -> templates)
  -> Missing-field detector (per selected template schema) -> asks user
  -> Renderer: docxtpl (DOCX template + data) -> .docx -> PDF (LibreOffice headless)
  -> Review/edit UI -> edit fields -> re-render -> new version saved -> download
```
- Core logic lives in an importable Python package `docgen/` with a CLI. UI and API are thin layers over it.
- Stack: Python 3.11+, docxtpl (+ python-docx for bootstrap/inspection), dateparser, pydantic, PyYAML, SQLite (SQLAlchemy or sqlite3), FastAPI for the API, Streamlit for the UI (fast to ship, easy for the club to run), PyMuPDF to rasterize PDFs for preview and visual tests.
- LLM provider must be pluggable behind an interface (`LLMClient`), configured by env vars (Gemini default, others swappable). The system MUST still work with no API key (form input + rules extraction only).
- Check the environment first: is LibreOffice (`soffice`) installed? Which OS? Are the fonts used by the samples available (Times New Roman, the Georgia-like serif on the ACM header)? If not, use metric-compatible fonts (e.g., Liberation Serif) and document it, so PDF output does not reflow. Tell me what I must install if anything is missing.

## 5. Canonical Event Record
Pydantic model, JSON-serializable, stored in SQLite. Every field is `{value, source, confirmed}` where source is one of `user | config | extracted_rule | extracted_llm | computed | default`.
Fields (extend as templates demand):
- `record_type`: event | meeting
- `event_name`, `event_code` (short code used in reference numbers, e.g., SIH; suggest, user confirms), `category`/`event_type`, `description`, `objectives`, `target_audience`
- `dates` (single or range), `time_range`, `venue`, `mode` (Offline/Online/Hybrid), `expected_participants`, `judges[]`
- `organizers` (from config, overridable)
- `budget_items[]` {item, amount}, `winners[]` {position, name, roll_no, course_semester, mobile, amount, bank{name_as_per_bank, bank_name, branch, account_no, ifsc, pan}}
- `bills[]` {supplier{name, gst_no}, invoice_no, invoice_date, items[] {name, qty, unit_cost}, tax {type, rate_or_amount}, payment{party, account_no, holder, bank, branch, ifsc}}
- `other_reimbursements[]` {name, account_no, ifsc, amount}
- `approval_note` {no, date} (produced by the Approval Note, consumed by the Bill Certificate)
- `meeting` block for MoM (see 7.6)
- `academic_year` (from config, e.g., 2026-27)

## 6. Template system
### 6.1 Folder layout
```
templates/
  permission_letter/  template.docx  schema.yaml
  prize_money_receipt/
  approval_note/
  bill_summary/
  bill_certificate/
  mom/
  _clauses/           reusable snippets (YAML/Jinja), e.g. venue_request_clause.yaml
config/
  club_config.yaml          (real, gitignored)
  club_config.example.yaml  (committed)
assets/  logos, letterhead images, fonts
```
### 6.2 schema.yaml spec (design a clean, documented format; this is the minimum)
```yaml
id: permission_letter
name: Permission Letter
description: Request to HoD for venue/room use
stage: pre_event                  # pre_event | post_event | meeting
triggers: [event, workshop, hall booking, room, seminar hall]
letterhead: acm                   # key into club_config.letterheads
numbering: {series: ROOM, format: "ACM/{short_year}/{series}/{seq:03d}", confirm: true}
depends_on: []                    # e.g. bill_certificate depends on approval_note.approval_no
repeat_per: null                  # e.g. winners -> one document per winner (batch)
fields:
  - {key: event_name, type: text, required: true, ask: "What is the event title?"}
  - {key: dates, type: date_range, required: true}
  - {key: venue, type: text, required: true}
  - {key: expected_participants, type: int, required: false}
  - {key: mode, type: enum, values: [Offline, Online, Hybrid], default_from: config.defaults.mode}
  - {key: brief_description, type: longtext, source_allowed: [user, llm_draft], required: true}
sections:
  - {id: venue_contacts, show_if: "venue_registry[venue].tech_assistant"}
```
Field attributes to support: `type` (text, longtext, int, money, date, date_range, time_range, enum, person_ref, table), `required` (true | false | conditional expression), `ask` prompt, `defer_ok` (see 8), `source_allowed`, `default_from`, `computed` (named function + args), `validate` (regex/range), `mask` (for sensitive fields).
### 6.3 Computed functions
A small registry in `docgen/functions.py` (sum, line_total, tax_amount, amount_in_words_inr, ordinal, format_inr (Indian grouping 1,00,000), format_date_range, short_year, etc.). Schemas reference them by name. Adding a new template normally needs none. Never use `eval` on user input; expression conditions use a safe evaluator.
### 6.4 DOCX templates
- Jinja tags live inside the DOCX (`{{ event_name }}`, `{% if %}`, table-row loops via `{%tr for %}`), so layout, tables, headers and footers (logo, letterhead, "Page X of Y" fields) are preserved.
- IMPORTANT: Word splits tags across runs. Write `scripts/build_templates.py` that GENERATES each initial `template.docx` programmatically with python-docx (letterhead images extracted from the sample PDFs via PyMuPDF placed in the header, tables with tags in single runs, correct fonts/borders/column widths), reproducing each sample PDF's layout as closely as possible. After that bootstrap, the club edits the DOCX in Word directly. Provide `docs/TEMPLATE_AUTHORING.md` explaining how (including the "type each tag in one go, paste as plain text" tip).
- Two letterheads exist: SVNIT (Approval Note, Prize Money Receipt, Bill Certificate with Form BC-R block) and ACM (Permission Letter, Bill Summary, MoM). Letterhead per template is selected by `letterhead:` and defined in club_config.
- Template validator (`docgen validate-template <folder>`): every tag in the DOCX must exist in the schema, every required schema field must be used in the DOCX, loops are well-formed, and a dry-render with dummy data succeeds. Run it automatically on startup and in tests.
### 6.5 club_config.yaml
Club name, chapter code (6/52), head of account, academic year, letterheads/logos/colors/fonts, office bearers (people stored once with roles, so the same person appears as "Student Head" in one document and "Chairperson, ACM" in another via per-template designation labels), faculty (Chairman, Co-Chairman), approval chain (Chairman F&SW, Associate Dean SW, Dean SW), venue registry (e.g., Seminar Hall 402: tech assistant, faculty in-charge, default addressee HoD CSE), standing defaults (Purchase Order = NiL, Advance = NiL, Laboratory/Office = Student Council), and numbering series with last-used counters. Seed names and designations from the sample PDFs. Leave mobile numbers and all bank details as placeholders for me to fill locally. Values coming from config defaults are shown in review as "defaulted from config".

## 8. Extraction, recommendation, missing info
- Extraction order: (1) regex/dateparser rules (date ranges like "14–15 October", durations like "two-day", counts like "around 120 students", known venues from the registry); (2) LLM with strict JSON schema output for what rules could not parse. Year inference uses the academic year but is flagged unconfirmed. Everything LLM-derived is tagged `extracted_llm, confirmed=false`.
- Recommender: use event type plus lifecycle stage. Pre-event: Permission Letter (+ Approval Note when budget or Dean-level approval applies). Post-event: Prize Money Receipts (if winners), Bill Summary, Bill Certificate (if bills). Meeting: Permission Letter + MoM. Explain WHY each document is recommended; allow the user to override.
- Missing-field detector: runs against the selected templates' schemas and returns a grouped checklist (field, which documents need it, a friendly question from `ask`). For the example sentence, it must flag at least: start/end time, event short code/ref number, faculty/venue permissions contact, mode, description/objectives (offer an AI draft clearly labeled "AI-drafted, review"), budget items (if an Approval Note is selected), and signatory confirmation.
- Fields marked `defer_ok` (bank details, PAN, signatures, winner roll no/mobile) can be explicitly "left blank for hand-filling" by the user. This is a deliberate choice, never a silent fallback.
- Narrative fields (description, objectives) are the only place LLM drafting is allowed, always labeled and always editable.
